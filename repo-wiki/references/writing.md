# 内容标准与示范

## 让文字承担解释

先用读者能理解的概念建立模型，再引入符号和源码位置。围绕因果关系写：为什么需要某个机制（有设计记录才归因作者），它如何工作，哪些输入导致哪些结果，调用方怎样使用。每一串函数名后应能说清它们之间传递什么、改变什么，而非只写“转调到…”。

页面类型有不同重点：

| 类型 | 应形成的解释 |
|---|---|
| 总览 | 系统解决什么问题、子系统如何协作、关键链路和分层导航 |
| 模块设计 | 核心模型、算法/状态、接口边界、场景演算与约束 |
| 运行链路 | 起因、逐层数据/控制变化、时序、结果、关键失败路径 |
| 接口参考 | 参数/字段、单位、所有权、调用上下文、返回值、副作用、用法 |
| 操作指南 | 场景、前提、具体输入与步骤、预期产物/现象、失败定位、修改与验证入口 |

同一事实可在总览中概述、在设计页展开、在接口页说明约束；用链接避免重复细节，不删掉不同阅读视角。目录只在长页需要导航时提供；标题要表达内容，不强制每页同一套章节。

## 三种常见不合格内容

- “有双缓冲，性能高、安全。”缺实际机制和保证范围。
- “A 调 B，B 调 C；未运行 target。”只有定位，没有解释数据或可观察结果。
- 一个页面用五个段落讲五个独立模块，然后每段都说“库内部不展开”。这是接入概览，不能作为这些模块的完整设计文档。

多贴源码、更多链接或更长段落本身不能修正这些问题。

## 示范一：把算法解释到能演算

以下是**虚构教学系统**，展示说明方式，不是任何仓库的实现事实。生成真实 Wiki 时必须替换规则并读源核实。

假设调度器记住上次已消费时刻 0 ms，当前时刻为 23 ms，有周期 5 ms、相位 0 的任务。若真实实现采用“窗口内到期任务合并派发”，则区间 (0, 23] 包含 5/10/15/20 ms 四个到期点，本轮只调用一次该任务。调用参数若是配置周期，则传 5 ms，不是 23 ms。消费者若按参数累计距离，将与按真实流逝时间累计得到不同结果，因此必须检查任务的时间契约。

| 情形 | 已跨过的到期点 | 本轮调用次数 | 读者应理解的区别 |
|---|---|---|---|
| now=3 ms | 无 | 0 | 尚未到期 |
| now=5 ms | 5 | 1 | 正常派发 |
| now=23 ms | 5、10、15、20 | 1 | 窗口合并，未逐次重放 |

这张表解释的是算法。诊断阈值是否改变派发必须另查分支；不能因变量名 catchup/dropped 就推断丢弃策略。图可分别表达 ISR/主循环职责和时间窗口，不需要把整套函数清单放进同一图。

## 示范二：把生成系统分成模型与事务

仅写“SQLite → IR → renderer → 发布”是总览。设计页应继续解释：IR 对象如何表示配置、哪些字段影响身份、renderer 得到什么输入、生成集合如何闭合、何时切换活动文件。以仓库实际的一项配置为例，给出输入字段、生成符号、消费入口；再用某一步失败说明 journal/rollback 的真实边界。

如果操作页讲“增加一个配置项”，要定位真实编辑入口/schema/模板或回调、说明重生成后的产物和检查方式。“修改配置后重新生成”不足以让读者动手。没有运行 GUI 不等于不能从事件处理与 Core 接口解释它；实际交互效果未验证可注明。

## 图、表、例子怎样配合

- 每个模块先满足 [两类必需 Mermaid](diagrams.md)：调用关系图与调用时序图，分别解释实际调用结构和具体场景的先后。这是硬性要求；结构图、状态图和数据流图按需要额外补充，不能替代其中任何一类。
- 结构图解释职责与依赖；时序图解释谁先调用谁；数据流图解释值经过哪些变换；状态图解释 guard/action/next。
- 表格适合字段、返回值、参数、状态条件、接口差异；连续大段枚举这些信息时考虑用表。
- 例子应能验证读者的理解：给定输入/条件，正文足以推导输出与副作用。示例数值、伪代码、命令模板明确标注，不能伪装成执行结果。
- 每张图前说明问题，图后解释关键关系、条件、抽象范围和源依据。按意义核对所有边，callback 看绑定与调用点，异步发送不代表完成。

## 事实与引用

源码确认运行机制；设计文档支持设计意图；推导写明前提；当前配置与库能力分别表达。目录和 graph 用于发现，不能从函数 fan-in 推导所有调用都被某层拦截。

核心事实附近放相对源码链接与行号，例如 `[派发实现](../../src/scheduler.c#L40-L76)`。相邻同源事实可合用章节来源，避免每个短句后都重复长路径。摘录保留真实代码，只截解释所需部分。对数据库可记录只读查询方法、表/字段及非敏感结果，不制造数据库行号链接。

路径存在、哈希匹配、Mermaid 可渲染都不证明结论正确。不要用一个已知事实的精确引用替整段未经核实叙述背书。把与本页有关的验证限制集中说明，不在每节重复泛化警告。

## 内容验收

读者能否解释本主题的核心概念、追踪一个正常场景和一个关键边界、理解接口/数据约束、找到正确的修改位置？规划的章节是否已实际展开，是否把应有子页压缩成提及或“不展开”？复杂页是否有帮助推理的图/表/实例，而非只有函数摘要？

逐页作实际判断；不为满足词数或标题数量凑内容，不因字数很多自动判合格。源码问题可单列“当前接入与限制”，同时保留对模块能力的系统解释。

## 写作单位与深度

每页作为独立任务执行：只加载相关工程概览、页面目标、证据卡和邻页边界，然后充分阅读本主题源码。上下文容量影响分批方式，不影响问题数量和展开深度；有不足就继续检索，复杂页可以经历多次研究、写作、复核。不要把预算用尽解释成“按计划完成”。

以真实模块为例组织三条阅读路径：设计解释对象与算法，参考解释类型/字段/契约，指南让读者完成一个端到端操作。它们可以分布在不同页，通过链接衔接。架构图不能替代 API 参数说明，代码定位不能替代 GUI 的输入步骤，缺陷列表不能替代模块教程。

图表与正文共同完成解释，目录阶段已为每个模块规划两类必需图，写该模块时一并完成。两类图齐全只是最低条件，不能因数量达标忽视错误的调用和时序；复杂机制按需要增加图。无成本限制时仍应删去无信息重复，而不是压缩有用解释。正文写作开始前必须已有完整工程分析和整体目录，不以“边写边了解工程”替代前期工作。

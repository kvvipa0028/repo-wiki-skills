# 知识地图与范围

## 从实际模块发现主题

1. 记录用户要求的仓库/子系统、读者、明确排除项。没有页数和时间限制时，不自行加入。
2. 在每个主根下建立完整文件清单，分批完整阅读源码、接口、配置 schema、构建选择、测试与相关设计资料，按 [前期流程](preparation.md) 记录。全部阅读与工程分析完成之后，才能进入模块分类和整体目录确认；不能用抽样、符号图或 README 代替全工程阅读。
3. 将全部独立模块登记为 modules，并以 coverage area 组织知识主题。不要把整个应用、所有工具或全部库填成一行“已在总览覆盖”。每个模块都有负责页及专属调用关系图、调用时序图；相关区域可以共享总览，但总览中的一句话或一张全局图不等于模块已完整解释。
4. 把跨模块运行链路单独作为主题，与模块内部设计互相链接。库内部算法、项目 adapter 和当前 variant 接线是不同视角，不要只解释接入点就跳过库本身。

## 按模块组织实际文件夹

输出必须按模块落盘。每个模块有唯一的 `modules[].directory`，为 Wiki 相对路径 `content/<模块>/` 或 `content/<领域>/<子系统>/<模块>/`（字段值不带末尾斜杠）。目录名可用中文或稳定英文名；模块 ID 与源目录不必同名，按分析出的职责分类。子模块可嵌套，但父模块不能把子模块目录中的页面登记为自己的页面。

```text
wiki/
├── README.md                   # 全局导航
├── REPORT.md                   # 交付状态
├── content/
│   ├── _overview/              # 跨模块架构总览
│   ├── _flows/                 # 跨模块运行链路
│   ├── system/
│   │   └── scheduler/          # 一个模块自己的目录
│   │       ├── README.md
│   │       ├── design.md
│   │       └── calls.md        # 可包含调用图和时序图
│   └── configtool/
│       ├── generation/         # 另一个模块
│       │   ├── README.md
│       │   └── publishing.md
│       └── feedback/           # 独立能力形成的模块
│           └── README.md       # 小模块可在一页讲全
└── _meta/                      # 阅读、规划、复核、渲染证据
```

示例只说明布局，不能照搬模块或固定页数。模块正文、指南、接口与两类 Mermaid 均放在所属目录，可有子目录；模块配套图片等资产也放该目录的 assets/。模块入口用相对链接导航到相关页面，根 README 按目录层级链接到各模块入口。

`content/_overview/`、`content/_flows/` 的公共页应列入 pages/coverage，不归入多个模块的 pages，不替代模块本身的说明与双图。根目录只放 README.md/REPORT.md 两个公共 Markdown 入口；其他正文必须进入模块或上述公共目录。实际新增 Markdown 也要入计划，不能把未规划内容遗留在目录外。

`plan/check/checkpoint/finish` 会拒绝缺失/共享模块目录、页面越过模块目录、子模块归属混乱；完成检查还会拒绝未登记正文。迁移原有平铺 Wiki 时保留原文，先规划新路径，再移动页面并修正全部相对链接及 review；不要直接批量改 state 掩盖搬迁。

## 独立能力不能被目录分组吞掉

在 analysis.modules[].capabilities 中登记实际独立能力及源码依据，再在 plan 中逐项映射到页面、独立标题和问题。识别依据包括公开接口、注册表、CLI 子命令、GUI 操作、schema、构建变体和测试分组；文件夹名不能代替能力发现。每个文件的阅读发现要与能力清单对照，覆盖复核再从仓库入口反查一次。

例如工具同时有配置编辑、生成发布、工作区恢复、反馈提交和更新恢复时，只写生成流程不能代表整个工具。可以共享总览，但每项能力需要机制、使用/失败场景及图中的对应路径。独立入口、状态、配置契约和消费者形成独立子系统时，应拆成模块并各自画两类图。同一模块的图可以覆盖多项能力，须说明实际路径；复杂场景继续拆图。不得为躲避双图要求故意粗化模块，也不按文件数机械决定页数。

## 拆页判据

一个独立概念/能力、复杂机制、接口集合或操作场景，能形成连贯的读者问题时可独立成页。若一个页面把多个模块每个讲一小段，继续拆；若子页只重复父页且无独立问题，合并。目录深度取决于复杂度，不能把“有 parent 字段”当作已形成有效层级。

下面是对复杂配置工具的结构示例，不是所有仓库必备标题，也不是 Qoder 内部规划证据：

```text
配置工具
├─ 总览：职责、用户流程与子系统边界
├─ 配置模型
│  ├─ Project / Variant 数据及继承
│  └─ Schema、版本迁移与编辑事务
├─ 生成系统
│  ├─ Frozen IR：模型与确定性
│  ├─ Renderer / 外部生成工具
│  └─ 发布、回滚和生成一致性
├─ 插件扩展：发现、契约、校验与新增组件实例
├─ GUI / CLI：各自操作场景及与 Core 的协作
└─ 安装、更新与控制服务：仓库实际存在的能力
```

上面的“生成系统”不能替代其他分支。实际不存在的分支不虚构；实际存在但本轮没读到的内容保持待办。

## 规划时考虑的内容

对每个 area 判断这些维度是否需要解释，可在 pages 的 questions/sections 自然表达，不额外创建逐项 coverage 表单：

- 领域概念、职责边界、典型用途；
- 关键对象/类型/字段、单位、所有权、状态；
- 算法或运行过程、上下游、时序、失败与恢复；
- 公开接口/配置及其约束；
- 一个实际使用/扩展/调试场景；
- 当前工程绑定、实现与设计差异、验证边界。

“问题驱动”是帮助发现知识，不是只允许回答初始三个问题。全工程分析后先规划全部分支，确认完整目录再写代表页。后续补读发现新机制、新子模块或未登记消费者时更新分析与目录检查点，再继续正文。对于已有参照 Wiki，按主题覆盖作对照并核实是否重复/过时，不按文件数量照抄。

## 完成边界

用户明确排除、生成缓存/二进制重复产物、没有独立语义的辅助目录可以说明后不展开。已初始化库只读并不等于不可分析；SDK 无需逐寄存器重写手册，但项目依赖的接口与约束仍应解释。

外部证据缺失与文章未完成分开：没 HIL 不妨碍完整解释已经读到的状态机；没读现有实现则不能只写“未验证”后把主题标 complete。用户范围不能因为当前模型上下文快满而缩小。

## 页面任务先校正事实假设

每页 objective 应描述读者结果，如“能按时间窗口推演一次调度，并正确配置任务”。questions 要覆盖实际能力，不套用产品类别的常见功能。基于已经完成的全工程阅读与分析，核对公开类型、入口和设计边界，区分已确认能力与限制。写作时仍可针对疑点再次读源；发现任务卡与实现冲突，修正任务卡和受影响父子页，不强行满足错误题目。

分支规划把设计、接口/配置参考、操作/排障视角都考虑到；不强制三个文件，但每个适用视角要有正文承接。一个独立库没有接入当前 variant，不代表它的公开能力可以遗漏。与已有参考 Wiki 对照时，逐主题解释合并、拆分或不适用的原因，不能只比较根目录数量。

完成前要从实际仓库重新发现一次：模块清单/submodule、源码目录、公开接口、schema/CLI/GUI入口、测试分组是否还有台账外的能力？再从台账到正文反查每个适用视角。自动库存只能发现文件成员变化，不能替代这次范围复核。

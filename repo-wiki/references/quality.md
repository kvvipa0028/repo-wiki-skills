# 质量复核与交付

验收的是读者能否从文章正确理解和使用工程，而不是文件、引用或图数。优先保证事实正确、独立能力覆盖、解释层次；token 仅在有真实 usage 时记录。没有成本限制时，不减少必要检索或复核，也不因成本停止剩余主题。

## 1. 每页必须实际复核

写完后切换为审阅视角，先看页面任务和正文能否回答读者问题，再回查关键源码，必要时重读之前看过的实现。每页都要做；代表页通过不能替代其他页面的验收。允许的情况下可用独立审阅者；没有代理或没有委派授权时，由当前执行者分开完成写作与复核，不能冒称独立审查。

| 核对项 | 实际要判断什么 |
|---|---|
| task_assumptions | 任务是否预设了并不存在的功能？库能力、项目绑定、未来设计是否混淆？发现错误就改任务和正文。 |
| source_fidelity | 关键结论是否由真实分支、公式、类型、注册和消费者支持？引用附近的源码是否真的支持这句话？ |
| explanation | 每个问题是否有因果解释、关键数据/状态变化和适用边界？是否只是“有此能力”或列出函数？ |
| examples | 算法/配置/接口/指南的具体输入是否足以推导输出、副作用与关键异常？数值和步骤是否与当前实现一致？ |
| diagrams | 所有图的边、方向、条件和抽象层是否与正文/源码一致？复杂关系是否仍缺必要图？语法/渲染是否真的检查过？ |
| scope_boundaries | 与父子页的职责是否清楚，适用版本/配置是否明确，指南是否可执行，验证限制是否准确？ |

每个 question 在 review 中记录正文的确切 Markdown 标题、正文摘录、已核对的具体结论、仓库来源文件及关键行段原文。不同问题不能复制同一个 conclusion；摘录必须存在于指定位置。一个标题可承接相关问题，但每项独立 capability 必须有自己的解释标题。正文找不到答案就继续写，不能删问题来让记录通过。发现问题保留在 open_findings，修复后重审。

examples 只有主题确实不适用才可标 not_applicable 并说明原因。diagrams 仅在不承担模块必需图的辅助页可标 not_applicable；每个模块的调用关系图与调用时序图不可豁免，真实无调用边界按 [图规范](diagrams.md) 表达。复核分别说明两类图的调用点、绑定与场景先后。必须执行 render 并修复 parser 错误；无渲染器可继续写作，但保留未验证、finish 不通过。

## 2. 从仓库反向核对完整覆盖

页面完成后，重新检查 scope.roots 下实际模块、manifest/submodule、接口、schema、配置/构建入口、测试分组。先从仓库到 coverage 找遗漏，再从 coverage 到正文检查深度，不能只浏览已有目录宣布完整。审阅材料必须包含真实仓库输入，不只使用自己写的计划和 report。

- 独立子系统、未被当前 variant 使用的库能力、跨模块链路、配置与操作路径是否有承接？
- analysis 的全部模块是否进入整体目录，是否各有真实且专属的调用关系 Mermaid 与 sequenceDiagram？是否有用全局图、状态图或普通流程图抵算时序图的情况？
- 每个适用的设计、接口/字段、操作/排障视角是否展开？父页的一句介绍不算子模块已解释。
- 同名对象的含义、单位、所有权、生命周期、错误返回、同步/异步边界是否跨页一致？重点检查同名页面、wrapper 与实现、配置与消费者。
- README 层级导航、页面互链和来源路径能否通达？发现孤立页、死链、重复页或“详见”没有承接时修复。
- 参照 Wiki 中有价值的主题是否被遗漏？参照中的错误、重复或过时主题有依据地处理，不按其页数机械复制。

将逐 area 的判断、负责页面、用于重新发现范围的源文件、跨页检查结论记入 scope review。所有缺项先返工。`scope-review` 记录计划、检查点、发现依据和文件成员版本；后续新增模块、修改计划或正文复核时旧范围验收失效。

## 3. 三种状态不可混淆

1. `check` 通过：前期分析/目录版本、链接、范围、围栏及必需图位置/类型等机械检查通过，不能证明阅读和图的语义正确。
2. `checkpoint` / `scope-review` 接受记录：实际审阅者提交了完整、可追踪且对应当前版本的复核记录。
3. 交付：脚本 `finish` 通过，且审阅者确实完成所有内容与覆盖核对，没有已知未解决问题。

脚本核对摘录、行段、图位置、渲染记录与历史，但不理解自然语言，不能识别所有编造的 review，也不能证明台账没有漏项。禁止自动为所有检查项填 pass、根据标题/长度合成 review，或重算哈希掩盖未复核变更。`ready_for_delivery` 是声明与版本门禁，不是质量评分。

交付报告分别列出实际范围、已完成、缺项/阻塞、内容复核、机械结果和未执行的验证。缺硬件不妨碍写完整的源码解释，但不能宣称已做 target/HIL。缺源码或仍未解释的问题意味着相应范围未完成，不能用一条免责声明改成完整交付。

## 禁止用修复验收文件代替修复内容

允许机械合并已完成的阅读记录、计算 hash、解析链接和渲染，不允许脚本生成判断结果。禁止 missing/unsupported→pass、所有问题复制结论、自动清空 open_findings。提交过的问题保留在 history；解决后在 resolutions 逐项说明改动/重新核验与源证据。引用失效先找真实论据，不能取首个同名 token 或截断到文件头/EOF 来通过检查。

scope review 的 capability_checks 逐项记录从真实入口反查独立能力的结果，不能用某个大目录的统一结论替代。任何一项失败都保持 draft/blocked 并继续可做工作。禁止改写校验脚本、版本号、手造 SVG/验收记录或删除 history 包装完成。
